# Product label OCR

Tesseract.js 7 and its Korean/English integer language models are self-hosted under `/ocr`, generated from npm dependencies before build. No uploaded pixels or recognized raw text are sent to an external AI provider. Language models may be cached in the browser; recognition results are kept in component state only.

Recognition is optional. Labelled manufacturer, product name, model, serial number and full valid manufacturing dates are extracted using conservative rules; incomplete/low-confidence output remains blank. Categories are suggestions based only on a clearly labelled product name. The score returned by OCR is not a calibrated field-accuracy percentage. Reflective/blurred/rotated/tiny text and alternative layouts may fail. Manual editing remains available.

Per-field evidence levels: HIGH >= 0.90, MEDIUM >= 0.60, otherwise LOW. Only HIGH fills the review inputs; MEDIUM stays blank until the user explicitly chooses that individual candidate. Logo/context-only brand matches are capped at MEDIUM. Identifiers require an explicit label, valid token syntax and agreement with a second sparse-text OCR pass before HIGH. Conflicting candidates are suppressed. Bounding boxes support a unique value to the right or directly below its label; ambiguous associations remain blank. Full manufacturing dates require an explicit manufacturing label, never an energy-label standard effective date. These thresholds are heuristic gates, not measured probabilities.

Real-photo regression inputs under `test-labels/` are private and Git-ignored. The supplied refrigerator and TV photos still have character-recognition failures. The previous mixed-column refrigerator model candidate is rejected rather than automatically filled. Production remains gated on further real browser and accuracy verification.

The review panel does not submit or save data. A user explicitly applies edited suggestions, checks the normal form and saves it. Existing nonempty inputs require overwrite confirmation. Manufacturing date and serial number are private nullable item fields. After successful item save the selected image is attached through the existing authorized Private Blob flow. An attachment failure does not create a second item: the saved item link and photo-only retry are offered.

An optional Gemini `gemini-3.8-flash` helper is gated to the isolated OCR Preview branch only. GET configuration never calls AI; the explicit authenticated Preview model-check query calls models.list without image analysis. POST requires an authenticated same-origin request, explicit `label-ai-v1` consent and a UUID request ID. Only the re-encoded label image and fixed extraction prompt are sent, never OCR text, account data or Home data. Re-encoding strips EXIF/GPS. Model output is validated; it remains a per-field choice, not a save or automatic overwrite. Browser OCR and manual registration still work without AI configuration.

The Preview-only `label_ai_preview.usage` operational ledger is separate from application tables and Prisma migrations. It stores request ID, day (Asia/Seoul), hashed user ID, status, token counts and estimated cost only. A transactional advisory lock enforces a GLOBAL 20-attempt daily cap across users/deployments; duplicate UUIDs are rejected. Failed/time-out attempts consume a slot because billing may already have occurred. There is one fetch attempt, no retries, no fallback model, no external search. A DB-host hash must match the isolated Preview DB or AI fails closed. Production is hard-disabled by deployment environment and branch checks, even if an enable flag is accidentally set.

Token-cost estimates use Gemini 3.8 Flash introductory input $0.75 / million and output $3.75 / million through 2026-12-31, then $1.50 / $7.50, including reported thinking tokens. Estimates are not invoices; failed calls with missing usage have unknown cost. Google paid API may retain data for safety; do not promise zero retention. Reference: https://ai.google.dev/gemini-api/docs/generate-content/latest-model.

Explicit authenticated Preview diagnostics are an exception to the normal no-retry analysis: fixed short text or one sanitized image, up to two retries ONLY for HTTP 503, 1s/2s exponential delays plus 0–499ms jitter. Each upstream attempt reserves a daily-budget slot. No retries for other HTTP codes or timeouts. Only redacted provider error status/message and HTTP history are returned; raw provider responses, keys and extracted content are not logged. Inline image requests must remain below 20MB. `LABEL_DIAGNOSTIC=1` in the test runner sends text first and sends the refrigerator image only after text HTTP 200; it never sends the TV image in this mode.

Normal Preview extraction also permits up to two HTTP-503-only budget-counted retries. Timeouts are never retried automatically. Images are re-encoded as JPEG quality 92, longest edge at most 1600px, no enlargement, with EXIF/GPS stripped. The upstream timeout is 90s per attempt with a 210s overall analysis deadline, below the route's 240s maxDuration on the verified Fluid Compute project. The browser has a 230s guard and offers manual re-analysis (new consent and request ID) on HTTP 504 or local timeout; results remain review-only. `LABEL_TEST_TV_ONLY=1` runs only the real TV image without sending the refrigerator again. Reduced byte size does not guarantee lower image-token billing or latency.

Sources: https://github.com/naptha/tesseract.js (Apache-2.0), https://github.com/naptha/tesseract.js-core (Apache-2.0), https://github.com/naptha/tessdata (language assets). Package versions are locked in pnpm-lock.yaml. Build scripts do not download models from a runtime CDN.

Release requires Preview browser recognition/review/manual-fallback tests, API validation/storage/ownership tests, mobile inspection, and additive migration verification. A generated label test is not a substitute for accuracy testing on representative real product labels.

## Browser OCR local revision (2026-10-14)

This section describes the earlier 456afa1 baseline. The local candidate below changes its crop comparison and conflict presentation.

Browser recognition now locates explicitly labelled model regions from the first layout pass before reading each region at two scales. If none is located, one sparse-text pass (longest edge at most 2400px) replaces the previous sixteen overlapping scans. The English reinitialization and additional enhanced scans are removed. No fixture coordinates, expected model lookup or look-alike character substitutions are used. Crop-only evidence is capped below HIGH; MEDIUM still requires review and existing/manual values remain protected by the form reducer. Missing or conflicting identifiers stay blank.

Successful browser results are cached by exact original-byte SHA-256 for five minutes, with at most three entries in page-session memory. Returned values are isolated copies; cancelled and failed analysis is not cached. The cache stores recognized results, not image bytes, and does not write to IndexedDB, disk, DB or Blob storage. Reloading the page clears it. Workers are still terminated after noncached analysis. A repeated analysis within the cache lifetime reuses the result; it is not a second independent accuracy check.

The local browser fixture check found refrigerator S839S30 as a MEDIUM proposal (not HIGH); TV 75UN7850KNA remains unresolved. These checks cover only the two supplied small fixtures, not M873GBB572 or phone performance. Production deployment remains a separate approval and requires broader real-label and mobile verification.
## TV model evidence and regulatory context (2026-10-14)

Primary product-model evidence excludes structured R-R-/R-C- regulatory IDs and explicitly regulatory, certification, radio-module, or Korean equipment-certification contexts. These are context rules, not a blacklist of model values: a separately labelled primary model remains valid even if the same value appears in a certification ID. The rule is shared by text extraction, model-region location and crop-evidence validation.

The supplied TV fixture is 664x512. Its actual model is in the upper white strip; the lower regulatory row refers to a different identifier. Diagnostic crops of the actual strip, scale variants, grayscale, normalization, sharpening, thresholding and inversion still confuse the second character 5 with S (for example 7SUN7850KNA), sometimes with high engine confidence. These diagnostic coordinates/transforms are not deployed recognition rules. Adding them as automatic fallbacks would add latency without proven accuracy and is intentionally avoided. TV recognition therefore stays blank; obtain a close, sharp original photo of the upper model strip or enter the verified model manually. Enlarging this compressed fixture cannot be treated as new character evidence.

## Local column and reading comparison candidate (2026-10-14)

This section records the 1300bc8 baseline; the raw-text priority revision below supersedes its auxiliary-conflict rule for explicitly labelled raw values.

Based on production commit 456afa1, this candidate stops model text at a subsequent explicit capacity/rating/serial/manufacturer column. It locates the first value to the right of a model caption, or a unique nearby value below a caption, and rejects a neighbouring column caption. A one-word caption no longer indexes beyond the OCR word array. Numeric-only values and certification/radio context still cannot become model evidence; no model lookup or 8/B, S/5 character substitution is used.

Detailed recognition has a fixed budget: at most two labelled regions, each read with mixed-language SINGLE_WORD at 4x, then English SINGLE_LINE at 4x and English SINGLE_WORD at 6x after one language switch. Whole-image layout and the existing optional sparse locator remain limited to two passes in total. Agreement across at least two distinct crop modes, with every valid crop score at least 60, allows at most MEDIUM. These are segmentation/language comparisons within Tesseract, not statistically independent OCR engines or calibrated probabilities. A different readable full-image or crop value forces LOW, retains up to four candidates for review and never auto-fills the model. Repeating the same mode alone cannot raise a crop-only candidate to MEDIUM. The existing manual/existing-value protection, cancellation and five-minute memory result cache remain active.

Actual Chrome component tests on the three supplied photos show: M873GBB572 is now present among LOW candidates alongside MB73GBB572, with the model input blank; S839S30 remains a MEDIUM proposal (0.67); 75UN7850KNA remains unresolved and its regulatory identifier is not auto-filled. This improves access to the correct M873 candidate, not reliable automatic recognition of all three photos. Tests use local self-hosted OCR assets without external AI, account writes or item storage. Desktop timings include component/import/worker processing and warm language assets; they do not measure phone or cold asset-download performance.

## Displayed raw model priority: local revision (2026-10-15)

The extraction policy below remains active. Its empty/manual-field protection is superseded for explicit photo recognition by the photo-priority form revision below.

At the user's request, a unique valid model value following an explicit model caption in the displayed first-pass text takes precedence over conflicting layout/crop readings. Model text ends before a following labelled capacity, rating, serial or manufacturer column. The exact recognized characters are preserved: MB73GBB572 stays MB73GBB572 even if a crop reads M873GBB572. There is no fixture lookup or character repair. Multiple different model values in the raw text, certification/radio context, numeric-only identifiers and bare unlabelled tokens cannot gain this priority.

An explicit raw model becomes a MEDIUM editable proposal with policy score 0.60, so the existing form reducer applies it only to an empty, untouched model field. This score expresses the requested source-priority/review policy, not measured OCR accuracy. Existing typed, cleared and prefilled values remain protected. Manufacturer extraction and application are independent and unchanged. The review message states that recognized values can be compared with the photo and edited; no candidate selection buttons are added.

`pnpm exec tsx scripts/test-raw-model-autofill.ts` covers raw/auxiliary conflicts, column separation, no character correction, multiple raw values, explicit-label requirements, regulatory exclusion, independent manufacturer application, existing/manual/cleared values and discard. These are synthetic pipeline tests using the real extraction and form reducer, not a new phone or production-browser photo accuracy measurement. This revision was validated locally before production deployment approval.

## Explicit photo priority in create/edit forms: local revision (2026-10-15)

When the user presses label recognition, eligible model and manufacturer proposals from that photo replace existing, manually edited or manually cleared values in both create and edit forms. Missing, empty and LOW proposals keep the current field value. The displayed-raw-model extraction and certification exclusion remain unchanged. Photo application affects only model and manufacturer: name, category, serial, dates, price and memo are untouched. The separate AI/legacy proposal action retains its prior empty-only behavior. Analysis does not submit or save the item.

Each successful photo application snapshots the values it actually overwrites, including typing done while OCR was pending. Discard restores the immediately preceding values; changes made manually after application are retained. Starting then cancelling another run keeps the previous photo's applied values. Selecting a replacement photo alone does not roll back or apply form values; it aborts and invalidates the previous OCR generation. A late, cancelled or replaced result cannot dispatch a new form update.

Run `pnpm exec tsx scripts/test-label-photo-priority.ts` for reducer transactions and `node scripts/test-label-photo-component.mjs` for the real create/edit form and capture event handlers with isolated hooks, UI dependencies and deferred OCR. The component regression deliberately resolves photo A after photo B, cancels pending work, replaces photos and verifies exact undo, missing-field preservation, post-analysis edits and unrelated date/price/memo values. It executes no DOM/browser engine, external AI, network or item-save operation. This revision was validated locally before production deployment approval.
